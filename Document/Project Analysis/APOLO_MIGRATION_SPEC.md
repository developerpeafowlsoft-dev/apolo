## 1. Purpose & System Environment

Migrating a decade of data (FY 2016-17 → 2025-26) out of a Windows desktop garment ERP into **Apolo**, a Laravel 11 multi-channel retail platform.

| | |
|---|---|
| **Target shop** | `id = 14` — Apolo Family Showroom |
| **Database** | `apolo_db_new` (MySQL, MAMP socket) |
| **Channels** | E-commerce web · Flutter app (REST) · Front-desk POS |
| **Local URL** | `https://apolo/` |

## 2. Standard Apolo Operational Workflow

Unchanged from v1, and still the path all *new* goods follow:

```
Inward Entry ──► Barcode GENERATED by Apolo ──► Purchase Voucher ──► Locked ──► POS + Online toggle
```

1. **Inward** — goods registered against a supplier; Apolo mints one barcode per unit.
2. **Purchase** — the inward challan is pulled in by voucher number, priced, and submitted. Once submitted it is permanently uneditable.
3. **Activation** — barcoded items are immediately scannable at POS. The *Online Sale* toggle in the Purchase Product List publishes an item to web and Flutter.

**The conflict this specification exists to resolve:** the barcode is *born inside Apolo*. Legacy stock already carries printed stickers, so pushing it through this pipeline would mint new identifiers and invalidate every sticker on the shelves.

## 3. Legacy Dataset — actual structure

> **Corrects v1 §3.** Folders are financial-year named, not `2017-18`; there is no `/Opening Stock` directory; the catalog folder is misspelled `Catelog` on disk.

### 3.1 Root

```
Web/backup_excel/
├── 2016-2017/ … 2025-2026/     10 financial-year folders
├── Master/                     Brand, Color, Department, Financial Year, HSN, Material, Size
├── Account/                    Account.xlsx, Opening Balance.xlsx, DayBook.xlsx
├── Catelog/                    Item Master.xlsx, Design Master.xlsx   ← note spelling
└── opening balance/            9 per-FY opening balance files
```

### 3.2 Kachi vs Paki — **critical**

Every report is exported twice, suffixed `k` or `P`:

| Suffix | Meaning | In scope |
|---|---|---|
| `P` / `p` | **Paki** (પાકી) — official, GST-compliant books | **Yes** |
| `k` | **Kachi** (કાચી) — unofficial / off-books | **No** — deferred |

`LegacyDataMigrationService::isKachiFile()` rejects `K`/`KACHI`/`KACCHI`/`KACHHI` as a standalone filename token, so an off-books sheet cannot be ingested by accident. Only `2016-2017/` ships both variants. The two barcode ranges do not overlap (verified: 0 collisions), so Kachi can be migrated later without colliding with the UNIQUE index on `product_barcodes.barcode_number`.

### 3.3 Per-year contents

Each FY folder holds four Paki exports. **Names drift between years** — the resolver classifies by keyword rather than matching filenames:

| Type | Observed spellings |
|---|---|
| Barcode | `Barcode Search P.xlsx` |
| Inward | `Voucher Wise INWARD P.xlsx` · `Voucher Detail Wise INWARD P.xlsx` · `Voucher Detail Wise INWART P.xlsx` *(typo, 2018-19)* · `Voucher Detail Wise INCHALLAN REPORT P.xlsx` |
| Purchase | `Voucher Wise PURCHASE P.xlsx` · `Voucher Detail Wise PURCHASE P.xlsx` · `Voucher Wise PURCHASE REPORT P.xlsx` |
| Sales | `Voucher Detail SALE P.xlsx` · `Voucher Wise SALE P.xlsx` · `Voucher Wise SALES P.xlsx` · `Voucher Wise SALES REPORT P.xlsx` |

Only the **detail** sale export carries a barcode per line; the voucher-wise one is a bill summary and can retire nothing. Several years ship both, so step 15 selects the detail file explicitly rather than relying on `findYearFile()`, which picks alphabetically and happens to favour `Detail` over `Wise` today.

The sale export is also the one file whose **structure** drifts, not just its name — see §3.6.

### 3.4 Barcode sheets are stock snapshots, not per-year deltas

Each year's `Barcode Search` lists barcodes *in stock during that year*. Barcodes appear and disappear as goods are sold:

| FY | Barcodes | New vs prior | Gone vs prior |
|---|---:|---:|---:|
| 2016-17 | 19,189 | — | — |
| 2019-20 | 29,697 | 14,695 | 11,540 |
| 2022-23 | 45,673 | 21,836 | 17,437 |
| **2025-26** | **46,662** | 23,634 | 25,303 |

Union across all years = **166,769** unique barcodes ever issued. **Naively summing the sheets (317,955) would be catastrophic duplication.**

### 3.5 Known data defects

| Defect | Impact |
|---|---|
| **`2024-2025/` is byte-identical to `2020-2021/`** (same MD5 on all files) | Must be re-exported before that year is replayed, or it double-posts |
| `opening balance/` missing **2022-2023** | Gap in the per-FY balance chain |
| `Account/DayBook.xlsx` (138 rows) has no migration step | Cash/bank/journal vouchers outside purchase and sales are not migrated |

### 3.6 The sale export changed shape mid-decade

`Voucher Detail SALE P.xlsx` is the only per-year file whose structure changes. Two shapes:

| | 2017-18 → 2019-20 | 2020-21 → 2025-26 |
|---|---|---|
| Title block | Two rows; header on **row 3** | None; header on **row 1** |
| Barcode | Column **K** | Column **J** |
| Columns from `Sales Type` onward | — | Shifted one column left |
| Voucher date | Excel serial (`42826`) | Text `dd/mm/yyyy` |

Read with the earlier shape's column letters, the later files yield `Company Barcode` where Barcode belongs, `Free Qty` (always 0) where Qty belongs, and `Gift Voucher Amt` (always 0) where the bill total belongs.

**The drift is confined to this one file.** Inward and purchase exports keep a row-3 header and Excel serial dates in every year — checked across all nine folders — so steps 12 and 14 are unaffected.

#### Several day books share one file

From 2020-21 the shop runs more than one voucher sequence at a time, and **each restarts its numbering at `00001`**:

| FY | Day books | Distinct voucher numbers | Actual bills |
|---|---|---:|---:|
| 2017-2018 | `GF` | 8,524 | 8,524 |
| 2020-2021 | `FF` `GF` `GF1` `SALE RETURN` | 5,739 | **11,024** |
| 2025-2026 | `FF` `GF` `GF1` | 6,246 | **10,638** |

A bill is therefore identified by **day book + voucher number**. Keying on the number alone silently merges unrelated bills — see §7.7.

#### Returns

`Sales Type` is `Sales` or `Return`. A return carries `Qty = -1` with negative amounts, and `R.Sales Voucher No` names the bill it reverses. **Some returns are booked twice against the same original voucher**, so quantities do not net to anything usable: a barcode's final state has to be decided by its last event, not by summing its signed quantities.

Across the decade: 294,006 data rows, of which 17,806 are returns.

#### The inward export also comes in two shapes

`Voucher Detail Wise INWARD P.xlsx` is what opening stock joins against (§6.2), and it too varies by year:

| Shape | Years | Carries |
|---|---|---|
| **detail** | 2018-19, 2019-20, 2020-21, 2023-24, 2024-25, 2025-26 | Voucher No, Date, Account Name, Mobile1, GST No, **HSN Code, Item Name, Size1**, Qty, Purc Rate, Sales Rate, Tax Name, SGST/CGST/IGST, Net Amount — *per item* |
| **summary** | 2017-18, 2021-22, 2022-23 | the same financials *per voucher*, with no HSN, item name or size |
| **none** | 2016-17 | no inward export at all |

Header on row 3 in both, and dates as Excel serials in every year — so unlike the sale export above, steps 12 and 14 need no special handling. Filenames drift as usual, including an `INWART` typo in 2018-19 and an Excel lock file sitting beside the real 2019-20 export.

#### Subtotal bands

Roughly one row in five is a `Voucher No Total` or `Grand Total` band carrying no bill of its own — 62,128 rows across the nine files. They are skipped on the voucher-number and day-book cells.

## 4. The Barcode Constraint

Every physical garment carries a printed sticker from the legacy system. Re-stickering is not viable on labour, cost, or downtime grounds.

**Therefore: the barcode is an import INPUT, never regenerated.** Both the opening-stock importer and Step 13 of the year replay read the barcode string verbatim from the sheet.

> **Corrects v1 §4.1.** v1 states "over 88,000 physical units". That is the client's informal estimate, not a system figure. The authoritative count is whatever the Paki snapshot holds — **46,662 at 31 March 2026**. Treat 88,000 as unverified; the gap is plausibly Kachi stock, which is out of scope.

## 5. Migration Strategy — the 31 March 2026 split

The single most important decision in this specification, and new in v2.

```
          ≤ 31 Mar 2026                    1 Apr 2026 → cutover
   ┌──────────────────────────┐      ┌──────────────────────────────┐
   │   OPENING STOCK          │      │   STANDARD FLOW              │
   │   one snapshot           │      │   full year replay           │
   │   barcodes preserved     │      │   barcodes preserved         │
   │   purchase stage BYPASSED│      │   inward → purchase → GST    │
   │   Dr Stock / Cr Equity   │      │   normal ledger postings     │
   └──────────────────────────┘      └──────────────────────────────┘
        FY2025-26 closing                    FY2026-27 live year
        = FY2026-27 opening
```

**Why this split:** closing stock of one year *is* opening stock of the next, so 31 March is the accounting-correct boundary. Everything before it collapses into a single opening position — no need to replay ten years to start trading. Everything after it is the live financial year and deserves a real audit trail.

**Hard ordering:** opening stock must load **before** the FY2026-27 sales replay. Those sales mark barcodes sold that arrived via opening stock; run them first and the `is_sold` updates find nothing.

**Self-correcting:** the 46,662 snapshot includes items sold between April and September. Replaying those sales marks exactly those as sold, landing on correct current stock with no manual reconciliation.

## 6. Opening Stock Module — as built

> **Replaces v1 §5 and §7.1.** v1 proposed a dedicated `opening_stocks` table with a POS `UNION`. That was **rejected**. See §12 for the reasoning.

### 6.1 Data model — no new table

Opening stock reuses the existing inventory tables, distinguished by one flag:

```sql
ALTER TABLE inward_invoices ADD is_opening_stock TINYINT(1) DEFAULT 0;
CREATE INDEX idx_inward_shop_opening_stock ON inward_invoices (shop_id, is_opening_stock);
```

| v1 proposed | As built |
|---|---|
| `opening_stocks` table | `inward_invoices.is_opening_stock = 1` |
| `barcode` column | `product_barcodes.barcode_number` (already UNIQUE-indexed) |
| `is_pos_active` | implicit — `product_barcodes.is_sold = 0` |
| `is_online_active` | existing `inward_products.is_online_product` |
| POS `UNION` of two tables | single path — POS already resolves via `ProductBarcode` |
| "deduct from the appropriate table" | one inventory path, no branching |

**Consequence: POS, the web storefront and the Flutter API needed zero changes.** Opening stock items arrive as ordinary `products` rows.

### 6.2 Every year, deduplicated

Opening Stock holds **one row per garment the shop has ever owned** — not the closing position alone. Each year's `Barcode Search P.xlsx` is read in order and the **first sighting** of a barcode wins; later sheets repeat it and those repeats are skipped.

| FY | Rows | New | Already seen | Running union |
|---|---:|---:|---:|---:|
| 2016-2017 | 19,189 | 19,189 | 0 | 19,189 |
| 2017-2018 | 25,131 | 15,098 | 10,033 | 34,287 |
| 2018-2019 | 26,542 | 12,406 | 14,136 | 46,693 |
| 2019-2020 | 29,697 | 14,688 | 15,009 | 61,381 |
| 2020-2021 | 35,456 | 18,390 | 17,066 | 79,771 |
| 2021-2022 | 41,274 | 20,757 | 20,517 | 100,528 |
| 2022-2023 | 45,673 | 21,832 | 23,841 | 122,360 |
| 2023-2024 | 48,331 | 20,789 | 27,542 | 143,149 |
| 2024-2025 | 35,456 | **0** | 35,456 | 143,149 |
| 2025-2026 | 46,662 | 23,620 | 23,042 | **166,769** |

First sighting matters: it keeps the year and challan the garment actually arrived on, rather than whichever later sheet repeated it. By 2023-24 more than half of each sheet is carried forward, so deduplication is doing real work. 2024-2025 contributes nothing — its sheet duplicates 2020-2021 (§6.4).

`--all-years` selects this mode; without it the importer reads the closing snapshot alone.

> **Why the whole decade and not just what is on the shelf.** A closing snapshot answers "what do we hold" but cannot answer "what happened to barcode X" — a barcode sold in 2022 simply is not in it, so the system has no record the garment ever existed. Loading every year and then letting the sale files mark what left gives both answers from one table.

### 6.3 Joining each barcode to its challan

The snapshot carries the item, cost components and markup; the inward challan carries the supplier, GSTIN, sales rate, tax name and the GST split. They join on **(financial year, voucher no, party)** — the year being essential because legacy voucher numbers restart at `00001` every April.

| | Barcodes | Share |
|---|---:|---:|
| Voucher + party matched | 138,996 | 83.3% |
| Voucher matched, party spelling differs | 1,188 | 0.7% |
| No challan — snapshot only | 26,585 | 15.9% |

Within a matched challan, each barcode is then placed on a specific line:

| Matched on | Barcodes |
|---|---:|
| item + size + rate | 80,449 |
| voucher only *(summary-shape years)* | 58,571 |
| unresolved | 26,585 |
| item + rate | 999 |
| hsn+size+rate · item+size · rate | 165 |

Every line records which rule matched it in `legacy_line_match`, so a sourced figure stays distinguishable from a fallback.

**Shape:**

| | |
|---|---|
| Inward challans | **4,831** — `inward_detail` 2,802 · `inward_summary` 1,865 · `snapshot_only` 164 |
| Inward product lines | **66,872** |
| Barcodes | **166,769** — no duplicates |
| Inward dates span | 2016-01-26 → 2026-03-31 |

### 6.4 Duplicate exports are refused by content

`2024-2025/Voucher Detail Wise INCHALLAN REPORT P.xlsx` and its barcode sheet are **byte-identical** to the 2020-2021 files. Reading them would attach 2020-21 suppliers, rates and GST to 2024-25 stock, and add 35,456 barcodes already loaded.

`LegacyInwardIndex` hashes each export and refuses any file it has already read, recording the year as `duplicate of 2020-2021`. Detected by content rather than by hardcoding the year, so a repeat in a future delivery is caught the same way.

### 6.5 What each line stores

Migration `2026_09_16_120000` added nine columns to `inward_products` and four to `inward_invoices`. **Every one is nullable on purpose** — three financial years ship only a voucher-wise inward export with no per-item rows, and FY 2016-17 ships none at all. There a `NULL` means *"the source does not carry this"*, which is worth distinguishing from a real zero.

| Column | From |
|---|---|
| `buy_price` · `net_purc_rate` · `mark_up` · `mark_down` | snapshot |
| `purcost_rate` · `pur_exp_rate` | snapshot |
| `tax_name` · `sgst_amount` · `cgst_amount` · `igst_amount` | challan line |
| `inward_sales_rate` · `inward_net_amount` | challan line |
| `legacy_line_match` | the join |
| `legacy_financial_year` · `legacy_party_gstin` · `legacy_source` · `legacy_voucher_resolved` | challan header *(on `inward_invoices`)* |

> **A zero is not a NULL.** The first cut used `$num('pur exp. rate') ?: null`, and in PHP `0.0 ?: null` is `null` — so genuine zeros were stored as "not in source". Now `isset($colMap[$label])` decides: NULL means the column is absent from the sheet, nothing else.

### 6.6 Accounting — valued on unsold barcodes

Opening stock is **not a purchase** — no supplier is credited and no GST is claimed, because tax on these goods was accounted for years ago in the legacy system.

```
JV-OS-20260401-R3    2026-04-01    FY 2026-27    posted

  Dr   OPENING STOCK            Stock-in-Hand / Inventory   ₹ 1,52,53,234.50
       Cr   Opening Balance Equity   Capital Account        ₹ 1,52,53,234.50
```

**Valued per unsold barcode, not per line.** The table holds every barcode ever owned, so summing all lines would put **₹3,95,14,889.30** on the balance sheet — most of it garments sold years ago. What the journal must state is stock actually on the shelf: the 47,926 barcodes still flagged unsold, at ₹1,52,53,234.50.

Per barcode rather than per line because a line's barcodes can now be *partly* sold — three received, one gone — so the line quantity no longer describes what is held.

**Corrections are posted as contra vouchers, never edits.** The position has been rebuilt twice, and each reversal stays visible:

| id | Voucher | | Amount |
|---|---|---|---|
| 1 | `JV-OS-20260401` | reversed | Dr 1,49,05,768.51 |
| 2 | `JV-000002` | contra → 1 | Cr 1,49,05,768.51 |
| 3 | `JV-OS-20260401-R2` | reversed | Dr 1,49,02,860.40 |
| 31918 | `JV-000003` | contra → 3 | Cr 1,49,02,860.40 |
| 31919 | `JV-OS-20260401-R3` | **posted** | Dr 1,52,53,234.50 |

Five vouchers netting to one correct position. Every report sums entries, so none needed changing. `opening-stock:journal --replace` performs the reversal and re-post.

The service asserts Dr = Cr inside the transaction and rolls back otherwise.

### 6.7 Opening Stock screen — `/shop/opening-stock`

Sidebar entry under *Catalog & Inventory*. **Thirteen columns carry all twenty-eight stored values**, each cell stacking a headline figure over its supporting ones:

| Column | Carries |
|---|---|
| **Item** | product name / code · HSN |
| **Supplier** | party / GSTIN |
| **Challan** | challan no / date · FY / source · match rule |
| **Barcodes** | the printed sticker numbers |
| **Qty** | qty / in-stock badge · sold |
| **Cost** | Pur. / net · cost · exp |
| **Margin** | ▲ mark-up / ▼ mark-down |
| **Retail** | MRP / sale rate at inward |
| **Tax** | tax name / SGST · CGST · IGST |
| **Net Amt** · **Online** | |

Nine summary cards including **Challan Linked**, **Snapshot Only** and **GST on Purchase**. Filters: search (barcode, product, party, voucher, challan no, GSTIN), online status, **challan status**, **inward FY**, stock status.

#### The barcodes are shown

The point of the whole exercise is that the printed stickers survive, so the screen lists them. Each line renders its barcode numbers as chips, with **sold ones struck through in red** — a part-sold line reads at a glance without opening anything.

They are fetched in **one query for the page's lines**, grouped by `inward_product_id`; at 25 lines × N barcodes a per-row fetch would be a textbook N+1. The chips wrap inside a capped, scrollable wrapper so a twelve-barcode line does not stretch the row.

> The cap belongs on an inner `div`, not the `<td>`. A cell set to `display: block` leaves the table row and takes the column alignment with it.

#### A dash is not a zero

`—` renders where the source carries nothing; `0.00` where it recorded a zero (§6.5). Headers are abbreviated with the full name on hover.

#### Responsive

Below 992px each row stacks into a labelled card, done in CSS on the one table via `data-label` rather than by rendering a second markup block — a duplicate block would put two `.rowCheck` boxes per line in the DOM and make every bulk publish count each row twice.

Cells use `grid`, not `flex`: a cell like **Item** holds a name and a code as two elements, and flex would sit them side by side instead of stacking them under one label.

> **The layout bug this exposed.** The table ran off the right edge with no scrollbar on it, because the table was never what overflowed — the page was. `div.app-main-outer` lays the main column out with `display:flex`, and a flex item defaults to `min-width:auto`: it will not shrink below its content. The table's intrinsic width propagated up and widened the page by **634px** at 1280, so `.table-responsive` never became the constrained element and never scrolled. Fixed with `min-width: 0` on the main column, scoped to this view.

| Width | Behaviour |
|---|---|
| 1440 | **all 13 columns, no scroll at all** — table 1038px in a 1038px wrapper |
| 1280 | 44px of scroll inside the card |
| below 992 | stacks into labelled cards |

The page itself never scrolls sideways at any width. Combining the columns is what removed the scroll: the 28-column version needed 1920px, or 1680 with the sidebar collapsed.

**Shared-product rule:** products are shared across 66,872 lines. A product only goes offline once **no** remaining opening-stock line still wants it online — otherwise unpublishing one line would silently pull others from the storefront. Publishing sets `products.is_online_product = 1` and `is_update_product = 1`, the exact filter `Api\ProductController` uses.

### 6.8 Analysis screens — vendor-wise purchase & sale, and the page behind each card

The register answers *what is in stock*. These three screens answer *where did it come from and how much of it moved*, and they make every summary figure openable instead of terminal.

| Route | Screen |
|---|---|
| `/shop/opening-stock/vendors` | One row per supplier: bought · sold · still on hand |
| `/shop/opening-stock/vendors/{id}` | One supplier by year, by item, by challan, by bill |
| `/shop/opening-stock/insight/{metric}` | The detail page behind each of the nine cards |
| `/shop/opening-stock/vendors/export` | The vendor table as CSV |

**335 suppliers · 166,769 units bought · 118,843 sold (71.3%) · 47,926 on hand at ₹1,52,53,234.50.**

#### Grain is the whole design

Three different questions are asked of the same rows, and each has its own grain. Mixing them silently multiplies figures by the line quantity:

| Grain | Table | Measures |
|---|---|---|
| **Barcode** | `product_barcodes` | units, sold, available, cost, MRP |
| **Line** | `inward_products` | stock lines, challans, distinct items, **GST** |
| **Order** | `order_products` | realised sales, tax, returns |

GST is recorded once per inward line. Summed across the barcode join it would be counted once per unit — ₹27.2 lakh becomes something far larger. So the vendor row is assembled from **three separate grouped queries merged on the party id** rather than one join that looks tidier and is wrong.

Cost per barcode is `inward_products.net_purc_rate` — the same basis the opening journal used (§6.6), so the reports and the ledger cannot drift.

#### What ties out

43 assertions, all matching: every card figure against its detail page, the vendor totals against the register, each breakdown against its headline, and the vendor list row against the vendor detail page. The one that matters most:

> **The sum of every supplier's on-hand cost equals the `OPENING STOCK` ledger balance to ₹0.00** — ₹1,52,53,234.50. A third independent route to the same number, after the two in §10.

One deliberate five-paise difference: the register card adds line totals (`net_purc_price`, ₹3,95,14,889.30); the insight page adds per-barcode rates (₹3,95,14,889.25). Same money, different rounding point. The page says so rather than leaving it to be discovered.

#### Realised sales cover 7.8% of what sold

Sold units come from the sale exports and cover every year. **Realised money does not.** Only FY 2025-26 was replayed into orders (§8.12), and of 118,843 sold barcodes just **9,223 reach an order line** — ₹28,66,885.35 net, ₹1,80,919.52 tax, 1,155 units returned. **101 of 335 suppliers have no traceable sale at all.**

The column is labelled as the window it is. It is not presented as revenue, and it is not what the sell-through percentage is built from.

> Returns carry their direction in `order_products.quantity` as a `-1` line, and those lines sit under **both** `completed` and `returned` order statuses. Netting by summing the signed quantity is correct; also filtering on `order_status` would double-count.

#### Three things the screens surfaced

1. **FY 2024-25: 4,775 units in, zero sold.** The first build hid this behind a `HAVING value > 0` that dropped all-zero groups. A year with stock and no sales is a finding, so the clause was removed — the "units here" column now also adds back to the register's total.
2. **GST on purchase exists for only 5 of the 11 years.** Six years show ₹0.00, matching the snapshot-only lines that never found a challan (§6.3).
3. **The financial year comes from the challan date, not the folder.** `financialYearOf($inwardDate)` — so the range starts at **2015-2016**, a year earlier than the earliest folder. Year labels are read from the data; nothing is hardcoded.

#### Performance

Nine card figures asked one at a time are nine full sweeps of 166,769 barcodes. They are asked in **one pass per grain — two queries** — by folding each metric's filter into its own aggregate instead of a `WHERE`:

```sql
SUM(CASE WHEN pb.is_sold = 1 THEN 1 ELSE 0 END) AS sold
```

Warm cache, 16 requests in 32.5s: register 2.7s · vendor report 2.3s · one supplier 0.8s · insight pages 1.5–3.3s · year-filtered 0.5s. The year filter cuts the scan to a tenth of the rows.

#### Responsive

Below 992px each row stacks into a labelled card, as on the register (§6.7). Below **576px** the label moves *above* its value instead of beside it:

> On a phone the shell's icon rail plus four levels of container padding leave the card **208px**. A 96px label column plus a figure like `2,178,517.85` needs 226px, so rows were losing their right-hand digits inside their own cells. Measured, not guessed — `scrollWidth` 226 against `clientWidth` 206.

The same pass fixed the register's own cards breaking mid-number on a phone — `39,514,` / `889.25` — by shrinking the value and forbidding the break.

## 7. Implementation Reference

### 7.1 Files

### 7.3 Execution limits

`runStep()` and `autoCorrectAccounts()` lift PHP's execution cap so the admin dashboard can drive them. Both guard with `function_exists('set_time_limit')` — the call is commonly in `disable_functions` on shared hosting, where an unguarded call would fatal rather than degrade. Neither touches Apache's `Timeout`, which is a server-config change.

### 7.4 &nbsp;Account correction is destructive

`autoCorrectAccounts()` **deletes every `account_balances` row for the shop** and rebuilds it from voucher entries alone. Balances imported from `Opening Balance.xlsx` that have no backing voucher are discarded — 65 rows, in the current ledger.

It now takes a `$dryRun` flag. The dry run executes the real correction inside a transaction and rolls it back, so the reported figures are exactly what a live run would produce rather than a parallel estimate that can drift from the logic it describes. It returns `balances_before`, `balances_after` and `balances_lost`.

Both entry points preview before writing:

- **CLI** — `--dry-run` reports without writing; a live run prints the row delta, warns how many balances would be discarded, and prompts (defaulting to *no*).
- **Dashboard** — the button fires a dry run first and shows the real numbers in the confirmation dialog, switching to a red warning state when rows would be lost.

If balances are lost anyway, re-run `--step=9` to restore them from the Excel source; it uses `updateOrInsert`, so it rebuilds cleanly without disturbing voucher-derived rows.

### 7.7 &nbsp;Step 15 — POS sales, rebuilt

Step 15 reads the detail sale export, groups its lines into one order per bill, posts a sales voucher, and sets `is_sold` on each barcode. Four defects, every one of them silent — no error, no warning, just wrong data. All fixed 16 Sep.

| # | Defect | What it produced |
|---|---|---|
| 1 | `streamXlsxRows()` hardcodes the header to row 3 | Row-1 header ignored, first two bills dropped, a **data row** promoted to header |
| 2 | Column letters hardcoded to the 2017-20 shape | Barcode ← `Company Barcode`, Qty ← `Free Qty` (0), total ← `Gift Voucher Amt` (0) |
| 3 | `parseExcelDate()` passes text to `strtotime()` | `18/10/2020` → **today's date**; `01/04/2025` → 4 January |
| 4 | Orders keyed by voucher number alone | Bills from different day books merged into one |

Defects 1–3 made 2020-21 onward import as zero-quantity orders, dated to the day of the import, with **no barcode retired at all**. Defect 4 is the largest by volume and cost roughly **33,000 bills** across those years — their lines, totals and customer absorbed into whichever bill was read first.

#### The fixes

- **`streamXlsxRowsAuto($path, $requiredHeaders, $callback)`** — new sibling of `streamXlsxRows()`. Finds the header by *content*: the first row containing every required label becomes the header, and the callback receives a `label => column letter` map. Step 15 requires `voucher no` and `net amt`, both present in either shape. `streamXlsxRows()` is untouched, so its 26 other call sites cannot regress.
- **`mapSalesColumns()`** — resolves every field from header labels. Lookups are **exact, not substring**, so `Item Name` cannot match `Item Short Name` and `Barcode` cannot match `Company Barcode`. This also fixed a long-standing CGST/SGST transposition: the old letters had them the wrong way round in both shapes, harmless only because the two are equal on intra-state sales.
- **`parseLegacyDate()`** — new; Excel serial *or* `dd/mm/yyyy`, and returns `null` rather than a wrong date so the caller decides what an undated row means. Agrees with `parseExcelDate()` on every serial tested. `parseExcelDate()` is left alone; steps 12 and 14 do not need it (§3.6).
- **Day-book keying** — orders are keyed `dayBook|voucherNo`, and the day book is carried into the generated codes: `POS-2025-2026-GF1-00001`, `SAL-2025-2026-GF1-00001`. Squeezed to alphanumerics, since one day book is literally named `SALE RETURN`. Nothing depended on the old format — no migrated POS orders existed, and `POSReturnService` resolves by exact `order_code`.
- **Discount** — now `Item Disc Amt` **+** `Add Less Amt`. Only the sum reconciles `Sales Rate` against `Amt With Tax`; the old detail branch dropped `Add Less` entirely.

#### Barcodes: skipped, not invented

The old code **created** a `product_barcodes` row for any sold barcode it could not find, with `inward_invoice_id = null` and `is_sold = 1`. Across nine years that is about **258,000 ghost rows** — the sale files name 261,034 distinct barcodes and only 2,539 of them exist in the table. The Opening Stock screen counts `is_sold` shop-wide, so it would then have reported a quarter of a million sold against 46,662 opening-stock items.

Unknown barcodes are now **counted and logged, never created**. The step returns `retired`, `restocked`, `unknown` and a 50-barcode `unknown_sample`, and a live run writes a `Log::warning` naming the shop, year, count and sample. Verified by running the real write path inside a transaction and rolling back: `product_barcodes` held at 46,662 and rows with a NULL inward invoice stayed at 0.

#### Final state is decided by last event, not batch order

Sales and returns used to be collected into two flat lists and applied one after the other, so a barcode returned in April and resold in May finished as *available* — the return batch landed after the sale batch regardless of dates. Running step 15 for 2025-26 in that form **undid 10 of the 54 flags** set by the reconciliation in §7.8.

`resolveBarcodeFinalStates()` now resolves each barcode to its last event, ordered by voucher date with file position as the tie-break for same-day events — the same rule §7.8 uses, so the two agree by construction. Each barcode lands in exactly one batch, so the order the batches are applied in no longer affects the outcome. Only the newest event per barcode is retained, so the cost is one entry per barcode rather than one per line.

Re-verified the same way: `is_sold = 1` now holds at **54 / 54** through the run.

> **Dry runs exercise this too.** Barcode resolution and the known/unknown lookups run on both paths; only the `UPDATE` is withheld. A dry run and a rolled-back live run of 2025-26 report identical figures — 10 retired, 903 restocked, 31,131 unknown.

#### Also fixed here

`product_barcodes` reads and writes are now scoped to the shop. `barcode_number` carries a **global** unique index, so matching on the number alone can land on a row belonging to another shop; an unscoped update would retire that shop's stock on the strength of this shop's sale file.

> **The FY 2025-26 postings have since been removed** (§8.12) — revenue was recognised with no cost of sales, in the year before the stock arrived. The defects below were real and the fixes remain in the code, which matters for any future replay; the vouchers they produced are no longer in the ledger.

#### The vouchers did not balance

Running step 15 live for FY 2025-26 posted 10,638 sales vouchers, and **463 of them were unbalanced** — the ledger out by ₹26,718.76. Three defects, all pre-existing:

| Defect | Vouchers | Effect |
|---|---:|---|
| The return branch never reversed GST — it posted `Cr Cash` / `Dr Sales` and stopped | 351 | each out by its own tax |
| IGST was never posted, in either branch | 0 today | latent; fatal on the first inter-state bill |
| Per-line rounding in the source | 112 | pennies, e.g. `73.00` payable vs `73.09 + 0.05 + 0.05` of parts |

Both directions are now built from **one table of legs** — a return is the same legs with Dr and Cr swapped — so the two branches cannot drift apart again. IGST has its leg. Sub-rupee differences go to `EXP_ROF`, the round-off account the GST service already uses; anything above a rupee is still absorbed but counted and logged, so a real error surfaces instead of vanishing into round-off.

After the fix: **0 unbalanced vouchers**, Dr = Cr = ₹6,08,62,662.58, with ₹1,498.77 of round-off across 5,747 entries — about 26 paise a bill.

> This was found *after* going live, by checking voucher balance rather than order counts. The dry run could not have caught it — it posts no entries — but the posting logic could have been read first. Worth checking balance as a matter of course on the remaining years.

#### Retail buyers do not get a ledger account

Step 15 called `findOrCreateAccountMasterForParty(..., 'debtor', ...)` once per named bill and **discarded the result** — every posting goes to `CASH_DRAWER`. FY 2025-26 alone minted **3,256 Sundry Debtors accounts that never received an entry**, and nine years would have reached ~13,000.

The chart already provides `CUST_WALKIN` for counter sales, and customer identity lives in `users`/`customers` (§7.8). The call was removed rather than gated: a named party ledger is only correct for a genuine credit customer carrying a balance between visits, and the legacy export gives no way to tell those apart.

The 3,256 empty accounts were deleted after confirming every foreign key — `design_masters`, `inward_invoices`, `tds_masters`, `account_balances`, `voucher_entries` — referenced none of them. A re-run now creates zero: verified by running the full step again and watching the chart stay at 490.

#### Still open

- **Row-at-a-time inserts.** Each sale line is its own `order_products` insert, and each order adds a voucher plus about four entries individually. A single year is roughly 100,000 individual statements; the write phase dominates the run. Chunked inserts would fix it.
- **Step 15 alone is per-year.** It resolves final state within the year it is given. A barcode sold in 2023-24 and returned in 2024-25 needs both years replayed in order, or §7.8 run afterwards, to end in the right state.

### 7.8 &nbsp;Sold-barcode reconciliation & legacy customers

The opening stock snapshot lists what the legacy system believed was on the shelf at 31 March 2026. Some of those barcodes also appear in the sale history — but **most of them were sold and later returned, which is exactly why they are back in stock**. "Appears in a sale file" is not "sold".

`legacy:reconcile-sales` makes one pass over all nine sale files and produces two independent outputs.

**Sold-barcode detection.** Each in-stock barcode's events are ordered by voucher date and the last one decides:

| | Barcodes |
|---|---:|
| In stock (shop 14) | 46,662 |
| Appear in a sale file | 2,539 |
| …last event was a RETURN — correctly in stock | 2,485 |
| …last event was a SALE — **flagged sold** | **54** |

The 54 are spread across the decade, worth ₹24,666 at their last sale price, and touch 51 products, 5 of which go fully out of stock. They are also a genuine conflict — the snapshot says on the shelf, the history says sold — so each one is written to the anomaly report rather than merely actioned.

Ordering matters more than it looks: sorting by row position instead of date gives 169 rather than 54, the two rules disagreeing on 139 barcodes. Netting quantities is not an option either (§3.6 — duplicated returns).

**Customer extraction.** The legacy `Account.xlsx` holds 457 ledgers and **every party account is a creditor** — there are no debtors at all. Retail customers exist only as an `Account Name` and `Mobile1` on the sale rows. Identity is the mobile, normalised so `+91 98250 47770`, `09825047770` and `9825047770` are one person.

```
distinct legacy mobiles   16,646     users      33 → 16,677
already in users               2     customers  15 → 16,659
created                   16,644
```

Names resolve to the most recent spelling; 69 mobiles carried more than one, and 13 are not ten digits. Both are recorded as anomalies, not silently corrected. `created_at` is backdated to each customer's first purchase.

**Passwords are left NULL deliberately.** The obvious route — the POS checkout's `UserRepository::registerNewUser()` — calls `Hash::make($request->password)`, which with no password supplied stores a valid bcrypt hash of the empty string on every account. These are migrated records, not registrations; they get credentials when the person actually signs up.

A pre-existing user whose phone happens to match a legacy mobile is **not** converted into a customer unless it already holds the customer role — five staff accounts share a placeholder number and would otherwise have been swept in.

Report: `storage/app/migration-reports/sales-reconciliation-2026-09-16.json` — all 54 barcodes with their last voucher and buyer, plus 136 anomalies.

## 8. Accounting Layer

New in v2 — not covered by v1 at all. Covers the chart of accounts, the reporting layer, and the GST and voucher services.

### 8.0 &nbsp;Chart of accounts

The legacy importer filed every unrecognised ledger name as a trade creditor and gave accounts a `rand()` code suffix, so the same ledger got a new identity on each run and punctuation variants became separate accounts.

**Fixed in `LegacyDataMigrationService`:**

- `resolveLedgerGroupId()` — maps ledger names to proper groups across 11 categories. Patterns are anchored so supplier names containing a keyword (`AKAR SALES`, `MANAVTA SALES AGENCIES`) still fall through to Creditors. Validated 30/30; only 4 of 381 genuine creditors would move.
- `deterministicAccountCode()` — stable, collision-checked code replacing `rand()` at all three creation sites.
- Normalised-name matching — `PURCHASE A/C` and `PURCHASE A/C.` now resolve to one account.
- Step 8's unmapped-group fallback now classifies by account name instead of defaulting to Creditors.

### 8.1 &nbsp;Opening balance sign convention

`Opening Balance.xlsx` gives the type in column D (`Credit` / `Debit`) and the amount in column C as a **positive magnitude**. Step 9 stored Credit as positive and Debit as negative — backwards.

`FinancialStatementService` reads the opposite convention:

```php
$opDebit  = ($opening > 0) ? $opening : 0;
$opCredit = ($opening < 0) ? abs($opening) : 0;
```

So every statement built from opening balances had Dr and Cr swapped. The visible symptom was cash: with `CASH ON HAND` stored at −₹6.34 crore, the balance sheet's `max(0, $cashBankOp + …)` clamped it, **reporting zero cash**.

Corrected to **Dr positive, Cr negative**, and the type match widened to `credit`/`cr`/`c` — previously anything that was not the exact string `credit` fell through to debit, so an export using `Cr`/`Dr` would have flipped all 65 rows. After re-import, Cash & Bank opening reads ₹5,32,92,064.45.

**20 misfilings corrected** (inventory filed as liabilities, expenses filed as income, trading results filed as payables, three supplier brands filed as capital/bank accounts). Six judgement calls remain open for the firm's accountant, plus five duplicate pairs pending a merge decision.

Full findings: `Apolo Ledger Audit` artifact.

### 8.2 &nbsp;Report performance

The accounting dashboard was effectively unusable: **86.8 seconds and 64,696 queries** for one page load — well past Apache's 300s ceiling under any concurrency. Four separate N+1 loops:

| Location | Pattern |
|---|---|
| `CanonicalInventoryService::getShopPhysicalSkuSummary` | ~12 queries per product × 4,132 products |
| `CanonicalInventoryService::resolveCanonicalProductId` | `Schema::hasColumn()` — a schema-introspection round trip — once per product |
| `FinancialStatementService::generateTrialBalance` | 3 queries per account × 490 accounts |
| `FinancialStatementService` COGS | a cost lookup per order line, plus lazy-loaded `$ord->products` per order |

All four now pre-aggregate into grouped lookups, and `calculateShopInventoryValuation()` is memoised per request — the dashboard and each statement asked for it twice.

Fastest path for the remaining ~2.7s on the four heavy reports is the 4,132-SKU PHP loop, not the database.

### 8.3 &nbsp;GST posting service

Four defects, all corrected:

1. **Four account codes did not match the seeded chart** — `CASH_COUNTER_1` vs `CASH_DRAWER`, `CARD_PAYTM_CLEARING` vs `EDC_CLEARING`, `UPI_PPE_CLEARING` vs `UPI_CLEARING`, `SALES_RETURN` vs `SALES_RET`. Since `getOrCreateSystemAccount()` looks up by code and creates on miss, the first POS sale would have created duplicate ledgers with **identical names**, splitting cash across two accounts.
2. **Sales returns assumed 18% GST** (`$returnTotal * 0.18 / 1.18`). Apparel is commonly 5% or 12% — HSN 6109 in this dataset is 5% — so every garment return reversed the wrong tax, and GSTR-1 credit notes with it. There was no IGST branch either, so inter-state returns reversed CGST+SGST that was never charged. Now reads the rate from the original sale's lines and splits by place of supply.
3. **`financial_year_id` hardcoded to 1** (2016-2017) on the credit-note path, `?? 1` on the sales path. Now resolved by date.
4. **`extractInclusiveTax()` was dead code** — a correct Rule 35 implementation sitting unused while both posting methods did their own arithmetic. The return path now uses it.

### 8.4 &nbsp;Voucher service

- **Voucher numbering had no row lock**, despite a comment claiming "locked inside the same transaction". Two tills billing simultaneously read the same `current_no`; because `voucher_no` is unique-constrained the result was a failed sale rather than corrupt data. Now `lockForUpdate()`.
- **`ensureBalanced()` used strict float equality** on rounded sums, which can reject a valid voucher when two equal rupee totals land on adjacent doubles. Now a 0.005 tolerance, and the exception names both amounts.
- **A reversed voucher could be edited**, re-applying balances on top of the reversal. Now refused.
- `applyToBalance(int $branchId, …)` was receiving `shop_id`. Renamed.

### 8.5 &nbsp;Financial year resolution — a regression and its fix

Activating only the current financial year (§11) broke five lookups that filtered on **both** date range and `is_active`:

```php
FinancialYear::where('start_date','<=',$date)->where('end_date','>=',$date)
    ->where('is_active', 1)     // worked only while all 11 years were active
```

With ten years now inactive, any **backdated** transaction fell through to the fallback — FY 2016-17. Purchases were most exposed, since they carry a supplier bill date.

Fixed in `PosCartRepository`, `PurchaseController`, `OnlineOrderAccountingService` (two sites) and `POSHistoryService`. Which year a transaction *belongs to* is decided by its date alone; `is_active` answers a different question — which year is *open for posting* — and must not filter the lookup.

### 8.6 &nbsp;What is sound

`OnlineOrderAccountingService` is the strongest service in the set: idempotency by voucher id then duplicate check, revenue-recognition gating so unpaid COD does not book revenue early, and separate delivery-income and round-off legs. The nine remaining services came back clean against every defect class above — no hardcoded years or rates, no float equality on money, and all account codes matching the seeded chart.

### 8.7 &nbsp;Reversal by contra voucher

`reverse()` used to adjust `account_balances` directly and flip `status` to `reversed`, leaving the original entries in place. Since **no report filters on status** — 43 aggregation sites across 5 services — a reversed voucher disappeared from balances while still counting in the trial balance, P&L and balance sheet.

It now posts a **mirrored contra voucher**: same accounts, Dr and Cr swapped, same amounts. That nets the original to zero in anything that sums entries, so no report needed changing, and both sides stay visible for audit. It is also how reversal is done in double-entry practice — you never un-post an entry, you post its opposite.

| | |
|---|---|
| New column | `vouchers.reverses_voucher_id` (migration `2026_09_15_193000`), indexed. `original_id` was not reused — the migration engine already stores legacy voucher numbers there. |
| Numbering | The contra takes the next number in the **same** series. No `seq_prefix` override: `upsertSequence()` keys on voucher type rather than prefix, so passing one would rewrite the prefix for every future voucher of that type. |
| Return value | `reverse()` now returns the **contra**, not the original. Its one caller is the unrouted `VoucherController`. |
| Idempotency | Reversing twice returns the existing contra rather than posting a second one. |
| `destroy()` | Refuses to delete an original while its contra exists — otherwise the contra's live entries would throw the books out by that amount. |

Verified end to end: posting ₹25,000 moved the trial balance closing totals, and reversing returned them to the exact starting figures — `97,786,169.27 / 47,329,145.81` before and after — with `account_balances` likewise restored.

A voucher reversed under the **old** scheme has `status = 'reversed'` but no contra. `reverse()` detects that and refuses rather than guessing. There are none in this database.

### 8.8 &nbsp;Sales voucher composition

Real orders follow `payable_amount = total_amount + delivery_charge`, where `total_amount` is tax-inclusive goods. The sales leg was derived as `payable − tax`, which **folded the whole delivery charge into Sales revenue** — overstating turnover and giving the shipping fee the wrong GST treatment.

Order `000005` shows the difference:

| Leg | Before | After |
|---|---:|---:|
| Sales | 2,505.52 | **2,370.25** |
| Delivery Charges Collected | — | **135.27** |
| CGST / SGST | 62.38 / 62.37 | 62.38 / 62.37 |
| **Dr tender** | 2,630.27 | 2,630.27 |

Delivery now credits `REV_DELIVERY`, and a round-off plug against `EXP_ROF` absorbs sub-rupee differences. Anything larger than ₹1 **throws**, naming payable, goods, delivery, tax and discount — a component that is not modelled (a coupon, say) should fail loudly rather than disappear into round-off.

Also corrected here: the tax legs were labelled "CGST 9%" and "IGST 18%" regardless of the actual rate.

**An earlier note in this document was wrong.** It said the method could build an *unbalanced* voucher. It could not: `total_taxable_amount` and `coupon_discount_amount` do not exist as columns, so the `??` fallbacks always fired and Dr always equalled Cr. The defect was misallocation, not imbalance.

### 8.9 &nbsp;Manual journal vouchers

`VoucherController` is a complete, validated JSON API for manual journal entries — list, show, create, update, reverse, delete, and a number preview — backed by the same `VoucherService` the automatic postings use. It was **imported in `routes/shop.php` but never routed**, and could not even be instantiated: `extends Controller` with no `use App\Http\Controllers\Controller;`, so PHP resolved it to a non-existent `App\Http\Controllers\Shop\Controller`.

Before routing it, one thing had to change. Every action took `shop_id` **from the request**, so one shop could have read and written another's ledger. All seven actions are now scoped to the signed-in shop: `index` filters on it, `store` overwrites whatever the caller sent, and `show`/`update`/`reverse`/`destroy` resolve through an ownership check that 404s on anything outside it.

Routed under `/shop/accounting/journal`, behind `checkShopOwner` — deliberately not `/shop/vouchers`, which belongs to the promo-code controller.

Verified: a `shop_id = 1` in the request body saved to shop 14; `index` returned only shop 14; and `show`, `reverse` and `destroy` all refused a shop-1 voucher.

There is still no UI for this — it is a JSON API. A journal-entry screen would be the natural next piece.

### 8.10 &nbsp;Voucher numbering across shops

Voucher numbers are issued **per shop** — `voucher_sequences` is keyed on `(shop_id, financial_year_id, voucher_type, branch_id)`, so every shop starts its own series at 1. But the unique index on `vouchers.voucher_no` covered **the column alone**.

So the second shop to post a given voucher type hit a duplicate-key error and lost the transaction. Shop 14's `Purchase` sequence carries no prefix and already sits at 8, so `000001`–`000008` were globally taken.

Scoped to `(shop_id, voucher_no)` by migration `2026_09_15_210000`. Branches inside a shop stay distinct through `voucher_range_start`/`voucher_range_end`, which seeds each branch's sequence into its own band — so the shop is the right boundary, not the branch.

The migration refuses to run if any `(shop_id, voucher_no)` pair already duplicates, and `down()` refuses to restore the global index if two shops have since shared a number.

Two lookups in the migration engine relied on global uniqueness — the step 14 and step 15 idempotency checks — and are now shop-scoped. The opening journal's check already was.

Verified: shop 14 and shop 1 both minted `000001` with no collision, while a repeat *within* one shop was still rejected.

### 8.11 &nbsp;Shop-scoped identity lookups

The Stage E rehearsal (§10) surfaced five lookups in the migration engine that matched a record by its business key **without scoping to the shop**:

| Step | Lookup |
|---|---|
| 12 | `inward_invoices` by `inward_voucher_no` (×2) |
| 14 | `inward_invoices` by `inward_voucher_no` (×2) |
| 15 | `orders` by `order_code` |

The last is the dangerous one. `orders.order_code` is **not** globally unique — only `uuid`, `payment_attempt_id` and `idempotency_key` are — and on a match the code proceeds to **update** that order. Step 15 could therefore have silently overwritten another shop's sale.

All five are now scoped by `shop_id`, and the orders lookup additionally by `pos_order = 1`. This is the same defect class as the voucher numbering in §8.10: a business key that is unique *per shop* being treated as globally unique.


### 8.12 &nbsp;Why no pre-cutover sales are posted

FY 2025-26 was replayed through step 15 on 17 Sep: 10,638 bills, 10,641 vouchers, Dr = Cr. A review of the result against ordinary accounting standards found it unsound, and the postings were removed.

**Revenue without cost.** The replay recognised ₹1,43,85,323.47 of sales and **no cost of goods sold** — a P&L at 100% gross margin. There is no COGS account in the chart and no posting path to one; 118,843 barcodes are flagged sold and inventory was never credited.

**And in the wrong period.** Worse than the missing cost:

| | Revenue | Stock / purchase Dr |
|---|---:|---:|
| FY 2025-26 | ₹1,43,85,323.47 | ₹0.00 |
| FY 2026-27 | ₹0.00 | ₹1,52,53,234.50 |

The goods were sold a year *before* the books say the shop acquired them. That is not a rounding problem — it breaches the matching principle outright.

Neither is a migration defect. Both follow from two deliberate choices that are individually sound and jointly contradictory: opening stock is dated at the cutover (§5), and the replayed sales predate it.

**Resolution: pre-cutover sales do not enter the ledger.** The 10,638 sales vouchers and their 47,382 entries were removed. What remains:

```
5 vouchers, all FY 2026-27, all 2026-04-01
  OPENING STOCK           Dr  ₹1,52,53,234.50
  Opening Balance Equity  Cr  ₹1,52,53,234.50
revenue recognised in any FY: ₹0.00
```

**Orders, customers and sold flags were untouched** — 10,643 orders, 34,916 lines, 16,659 customers, 118,843 sold barcodes. A barcode still resolves to its bill, date, customer and price; the record simply carries no accounting legs. This works because the sold flags come from `legacy:reconcile-sales` reading the sale files directly, never from the vouchers.

> **Deleted, not reversed by contra** — a deliberate departure from §8.7. Contra restates a position that legitimately exists, which is why the opening journal carries a five-voucher chain. These postings should not have existed in this ledger's periods at all, no statutory return had been filed on them, and 10,638 contras would have trebled the ledger to net exactly zero. Backup: `storage/app/backup-before-reversing-fy2526-vouchers-20260917-131728.sql`.

**Replaying the remaining eight years would scale the defect, not fix it** — nine P&Ls at 100% margin instead of one. The stock and customer questions those years answer are already answered: step 4 flagged all 118,843 sold barcodes from all nine sale files, and all 16,659 customers are loaded. What a replay adds is ledger postings, which is exactly the unsound part.

#### Still to settle before go-live

**No COGS mechanism exists.** Once trading starts in FY 2026-27, each sale must reduce inventory and recognise cost. There is no COGS account and no posting path. This needs an accounting decision — perpetual (Dr COGS / Cr Inventory per sale) or periodic (Opening + Purchases − Closing at year end) — before the first live sale, not after.

**Why the separate table was rejected.** Three reasons, all from the existing code:

1. POS already resolves scans through `ProductBarcode`. A `UNION` across two differently-shaped tables adds a second code path to the hottest query in the business — the one v1 §7.1 wanted under 50ms.
2. v1's own "centralized handler to deduct from the appropriate table" doesn't stay in one place. It leaks into POS sale, POS return, web checkout, Flutter API, stock valuation, GST reports and barcode reconciliation — a permanent two-branch query in each.
3. The capability already existed. The migration engine's opening-stock mode already read legacy barcodes verbatim, preserved the strings and skipped the purchase voucher. What was missing was a UI and a flag, not a data model.

A separate *screen* was the real requirement, and it was built exactly as v1 described. A separate screen does not imply a separate table.
